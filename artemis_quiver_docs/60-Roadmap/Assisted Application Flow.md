# Assisted Application Flow: the Quiver-side proposal

> [!WARNING] Nothing here is implemented, and this is a proposal rather than a plan
> No code in `src/` was changed for this document. Every statement about current
> behaviour was read out of this repository on **2026-10-16**. Where a section
> says "decided", it means the design question is settled; it does not mean the
> work is scheduled or that Bruno has approved the scope.

> [!NOTE] Scope, and a deliberate boundary
> The authoritative, cross-repository specification is
> `F:\Dev\dispatch\28-assisted-application-flow-spec.md` (committed `dd55a2a`,
> 2026-10-16). **This page is the Quiver-side view only** and does not duplicate
> it: the Flow endpoints, the database tables on Flow's side and the write-back
> file handling all live there. This page is written to stand alone for a reader
> who only has this repository.
>
> **This repository is public.** So this page records what changes in Quiver and
> why, and it deliberately reproduces none of the personal career material the
> specification works from: no claims register, no enumerated false claim, no
> client or employer name, no application history. Where that material is the
> reason for a design decision, the failure class is described in the abstract
> and the detail is left where it lives, outside this repository. That boundary
> is the same one [[../20-APIs/Fabrication Surface Analysis|Fabrication Surface Analysis]]
> already draws, and for the same reason.

## 1. Where the idea came from

Quoted verbatim, as given by Bruno (project owner), because the shape of the
feature follows from the second message almost directly. Typos and all.

> I would like to think trough or experiment with automating a bit of this. Could we leverage flow and quiver to automate something like this?
>
> Flow already reviews a ton of jobs, but we could refine it a bit more to gather the absolute great jobs to apply... maybe we could automate analysis and cv generation?
> I mean, if we could just mass apply to lower grade jobs just to bulk, that would be great too to be honest.

> I've been thinking and it would be nice to have a "man in the loop" process.
> Flow searches for jobs with autopilot since we are on quiver. When we click "start applying" it opens the first job with the sidebar open, and starts pre-filling fields. User can approve, modify or reject each field. Whenever a field with a question to complete is reached, we call the llm to generate a response.
> For cv upload maybe we click the upload button so the user can select the file? or we recommend a cv to apply, generated by quiver.
> Let's spec this out.
>
> User would also need an option to skip any application by tagging it as applied, not applied and archive manually, as they might see things that flow missed. And it would be nice if they can see the reason for the job being high on top of the sidebar?
>
> Let's see how we can automate as much as possible of the process. Draft a plan and let's brainstorm

Two things in that second message became constraints rather than features. The
human in the loop is not a convenience setting: **the tool never clicks submit**,
in any phase, behind any flag. And the request to see "the reason for the job
being high" turned out to be the cheapest valuable part of the whole design,
because Flow already computes and serves that reasoning and nothing in Quiver
reads it.

## 2. What the feature is, from Quiver's side

Flow builds a queue of pre-vetted applications. Quiver opens each one in a tab
with the side panel beside it, shows why the job ranked, reads the form for
disqualifiers, lets the user approve or edit each pre-filled field, and records
the outcome automatically rather than relying on the user to write it down
later.

What changes in this repository:

| Area | Change | Status |
|---|---|---|
| `src/app/db/schema.ts` | Dexie `version(4)`: two new stores, `applyQueue` and `applyOutbox` | decided |
| `src/app/services/flowBridge.ts` | `FlowJobSummary` / `FlowJobDetail` gain the nine consensus, gate and eligibility fields Flow's API already returns | decided, trivial |
| `src/app/pages/Flow.tsx` | A **Start applying** entry point that pulls a queue and writes `applyQueue` | decided |
| `src/extension/` | New `ApplyQueue.tsx`: queue navigation, the rationale panel, five outcome tags | decided |
| `src/extension/formPageScripts.ts` | New `scanGateFields()`, reading the fixed-choice fields `scanFormFields()` deliberately skips | decided |
| `src/extension/ats/` | Per-ATS adapters, dispatched on an identity passed in from Flow | decided, phase two |
| `src/extension/background.ts` | Outbox drain with backoff, plus a `chrome.alarms` tick to survive service-worker eviction | decided |
| Free-text generation | Gated on a validator that lives outside this repo | open, see §6 |

It is **not** a replacement for [[Application-Assist|Application Assist]]. That
document is the Quiver-internal design for the CV folder, the form profile, and
review-and-fill, and it is good. It stops at Quiver's boundary: it has no
concept of a queue arriving from Flow, no gates, no write-back, and no scoring
rationale. This page adds the parts that cross the boundary and defers to it for
panel mechanics.

## 3. The handoff finding, which is the central architectural result

**The Flow-to-Quiver handoff needs no new transport.**

Quiver's SPA runs at `chrome-extension://<id>/index.html`. The SPA tab, the side
panel, the popup and the background service worker are therefore **one origin
with one IndexedDB**. This is not a new observation and it is not speculative:
`src/extension/idbProfile.ts` already depends on it in production and documents
it in a comment at the top of the file, which reads, in part, that the web app's
IndexedDB "lives on the SAME origin as the background service worker", which
"lets the background read the active profile directly instead of round-tripping
through an open app tab". `background.ts` corroborates it from the other side,
locating the SPA with `chrome.tabs.query({ url: chrome.runtime.getURL("index.html") + "*" })`.

So the queue is **a Dexie table plus a service-worker drain**. The SPA writes
`applyQueue`, the side panel reads it and writes item state and `applyOutbox`,
and the service worker drains the outbox to Flow over HTTP. One writer per
field, which is what makes resumability work without a reconciliation algorithm.

Three alternatives were considered and rejected:

| Option | Verdict |
|---|---|
| `externally_connectable` | **Rejected.** Not in the manifest and not needed. The SPA is not a web page. Adding it would open a messaging surface to every page on a matched origin, for no gain. |
| Content-script relay | **Rejected.** Content scripts lost the CORS exemption in MV3, and a relay adds a failure mode (no content script on a `chrome://` or store page) in exchange for nothing. |
| Side panel fetching Flow directly | **Not preferred.** The manifest already carries localhost host permissions, but Flow's CORS allow-list does not include a `chrome-extension://` origin, and **whether an MV3 extension page retains the host-permission CORS exemption the service worker has was not verified.** Outbound HTTP therefore goes through the service worker, which is known to have it. |

A consequence worth stating: the rationale fields travel **inside** the queue
payload rather than being fetched per job. A queue item has to be workable with
Flow down. The panel shows a snapshot with the build timestamp and a refresh
button; Flow is not a per-interaction dependency.

## 4. Per-ATS adapters, and why the ATS identity is passed in

**Decided: one adapter module per ATS, dispatched on an identity supplied by
Flow. No DOM sniffing to decide which adapter to use.**

Form structures differ predictably across Greenhouse, Ashby and Lever, and
generic DOM inference across all three is fragile. Quiver has no ATS-specific
form code today. `formPageScripts.ts` is entirely generic: label resolution
walks `autocomplete`, then `label[for]`, the wrapping `<label>`,
`aria-labelledby`, `aria-label`, `<legend>`, `placeholder`, and finally the
nearest ancestor with short text. The only per-ATS knowledge anywhere in the
extension is `ApplyAssist.tsx`'s two hard-coded origin patterns and a slug
sniffer for two board URL shapes.

The identity should not be inferred here, because **Flow already has it**. Flow
carries `jobs.ats_identity` on the row, written at ingest and backfilled for
pre-existing rows, in the format `"{ats}:{board}:{job_id}"`, which is exactly
the shape an adapter needs. It is simply **absent from the API response**:
neither of Flow's two job serialisers includes it. Adding it there, and
parsing it once server-side into `ats`, `ats_board` and `ats_job_id`, is a few
lines and means Quiver never splits the string.

The division of labour is the part worth writing down as a rule:

- **Adapters own the structural, board-independent part of a form**: which frame
  holds it, where the resume input is, the selector for the first-name field,
  how this ATS renders a yes/no.
- **The generic scan owns the per-posting part**: this employer's three custom
  questions. No adapter can enumerate those, and trying to make one is how
  per-ATS code rots.

`generic.ts` stays as the fallback and is today's behaviour unchanged, used for
unrecognised boards and as a second pass behind each real adapter.

When an adapter fails on a board, the cheap fix will look like sniffing the DOM.
**That is the wrong fix.** The right one is that the identity was null or wrong
upstream, and it gets corrected in Flow's URL resolver.

## 5. File upload: the human picks the file, and the rejected option gets its hearing

**Decided: Quiver surfaces the recommended CV and the user performs the file
selection. This is a decision record, so the rejected option is recorded
honestly, including the part of the original premise that is wrong.**

The premise offered for keeping the human in this step was that a browser
deliberately prevents a file input from being populated programmatically, as a
security boundary. **That is true of page JavaScript and not true of an MV3
extension**, and this repository already ships the code that does it:
`src/extension/formPageScripts.ts` exports
`attachFileToInput(id, base64, filename, mime)`, which builds a `DataTransfer`,
assigns `el.files` and dispatches bubbling `input` and `change` events.
`ApplyAssist.tsx` calls it, there is a unit test for it, and
[[Application-Assist|Application Assist]] calls it "the real path". The security
boundary is real but narrower than the sentence: a *page* cannot synthesise a
`File` from the user's disk because it has no read access to it. An extension
granted a directory handle has the bytes.

The decision nonetheless stands, on three grounds, and the reasoning is the
point of recording it:

1. **It fails silently and unevenly.** Some uploaders bind to a drop zone with
   no reachable input, some re-read the input on a framework event a synthetic
   one does not match, and some validate server-side in a way that rejects the
   result. `attachFileToInput` has never been tested against a live Greenhouse,
   Ashby or Lever form. A silent upload failure on a submitted application is a
   worse outcome than two keystrokes.
2. **It is the step where the wrong document gets sent**, and that is the one
   mistake in this flow that cannot be withdrawn. **The file choice is a
   deliberate checkpoint, not a limitation.** A tool that attaches documents
   unattended removes the last human review of what actually goes to an
   employer, which, given the generator defect this repository discloses and has
   not fixed, is exactly the review that should not be removed.
3. **It is not on the critical path.** It buys two keystrokes.

**Consequence as specified:** `attachFileToInput` stays in the codebase as an
opt-in, off-by-default **Attach** button next to a **Copy path** action,
labelled experimental. Nothing in the queue flow depends on it, and the
drag-and-drop drop-zone fallback should not be built.

One Quiver limitation that shapes the default path: the File System Access
handle Quiver holds (`cvFolder.ts`, `showDirectoryPicker`) is a **capability
handle, not a path**, and there is no `chrome.*` API to reveal a file in the
system file manager. So the absolute path a user would paste into the file
dialog has to come from Flow, which is a local process and can resolve one. If
Flow is unreachable, the panel degrades to showing the filename and folder name,
which is what `ApplyAssist.tsx`'s CV section does today.

## 6. The validator as a runtime gate

[[../20-APIs/Fabrication Surface Analysis|Fabrication Surface Analysis]] §3
identifies the defect underneath the other three surfaces: **nothing in `src/`
validates generated output against source facts at generation time.** A
fabricated claim is not an error condition in this codebase. It parses as
success, renders, and exports.

This feature is the natural place to close that, because it is the first point
in the product where generated text is about to be shown with the explicit
intention of sending it to an employer. The order is the whole feature:

```
draft  = generate(question, maxLength, profile, job, rules)
result = validate(draft)
if (result.violations.length) panel.showBlocked(result.violations)  // the violation
else                          panel.showDraft(draft)                 // editable, then Insert
```

**Generate, validate, then show, or show the violation instead of the text.**
Never generate, show, then validate. On failure the panel shows the rule, the
severity, the explanation and the matched substring with its context, and offers
**Regenerate** and **Write it myself**. There is **no "insert anyway"**: a
one-click override on the highest-severity class of violation is the same as not
having the gate, and the friction is the feature. The draft is re-validated on
insert, after edits, because an edited draft is a new artifact.

**The validator and its claims register live outside this repository, and are
loaded by configured path.** The reason is the public remote, not a packaging
preference: anything checked in here is published. So the validator runs on
Flow's side behind an endpoint, loading the module from a path given by an
environment variable, and **no rule, pattern or register entry is copied into
this repository or into Flow's.** If the register cannot be loaded, the endpoint
reports that and **the panel disables drafting entirely** rather than drafting
without a gate. Fail closed.

This is the same separation already settled for Flow's personal search rules,
applied to a second case, and it is consistent with the rule in `AGENTS.md`:
the personal deny-list is one person's tool and does not belong in a product
meant for any user. Quiver's own generic answer to the same problem, flagging
generated claims that do not appear in **the user's own profile**, remains
proposal 5 of the fabrication analysis and is unaffected by this feature.

Two honest conditions on all of it:

- **The gate is necessary and not sufficient.** The validator has open
  structural defects of its own, tracked outside this repository, and until they
  are fixed its recall on its highest-severity rule is worse than it looks.
  Shipping generated answers behind a gate that is open in the worst place is
  arguably worse than shipping nothing, because it attaches a validated-looking
  tick to text that was not meaningfully validated. That is why generation is
  phase three and not phase one.
- **An LLM-based verifier is not an option.** The fabrication analysis settles
  it: a verifier of the same class as the generator shares the generator's
  priors. The gate has to be deterministic.

## 7. Phasing

### Phase one: know what you applied to, and do not open what you must not

Phase one ships the **scoring rationale panel**, the **hard gates**, and
**automatic write-back**, and fills **no fields at all**. It calls no LLM,
touches no file input, and never clicks submit.

The rationale panel is a handful of type fields and one component over data Flow
already serves: score, consensus spread, pass count, the verbatim fit reasoning,
the eligibility verdict with its evidence quote, and the list of gates that were
checked with the sentence that produced each verdict. Three rules on it that are
not cosmetic:

- **Spread is always shown next to the score**, never behind a disclosure. Above
  a threshold the panel says the model disagreed with itself and collapses the
  rationale text, because a rationale kept from one of several disagreeing
  passes is a rationale for one verdict, not the consensus.
- **If Flow says the score is not comparable, no score is shown**, only the
  reason. Flow derives comparability server-side so every consumer agrees;
  do not re-derive it here.
- **A gate that could not run renders differently from a gate that passed.**
  "No evidence" is not "clear", and the panel must not let those look alike.

**Reading the form is in phase one deliberately.** This is the one piece of form
reading phase one needs, and the argument for it is empirical rather than
architectural: **disqualifying requirements have repeatedly appeared in required
form fields rather than in posting text**, and were caught late each time. A
phase one that opens a form, shows the rationale and takes an outcome tag, while
being blind to a disqualifier sitting in a required radio button on that same
page, reproduces the exact failure the gates exist to prevent.

It is also much less code than filling. No form profile, no aliases, no model,
no fill, no adapter: one injected scanner plus a dictionary pass. The scanner is
the part `scanFormFields()` deliberately skips today, whose docstring records
that fixed-choice fields "are deliberately ignored" because they are quick to do
by hand. That reasoning is correct for filling and wrong for gating, because the
disqualifiers live precisely there: a required sponsorship radio, an in-office
day-count checkbox, a country `select` whose options are a closed list.

Two further rules on the form gate:

- **It runs immediately after the form is located, before the first fill call
  and before any LLM call.** If filling can begin before the read completes, the
  gate does not exist.
- **No LLM in the gate.** A gate whose verdict depends on a small model reading
  a label is not a gate. An unrecognised required fixed-choice field is surfaced
  as a question for the user to read, not guessed at.

The gate pattern dictionary is loaded from a configured path outside this
repository and served to the panel with the queue. **Quiver ships no copy of
it.**

### Phase two: pre-fill, no generation

The three ATS adapters and the generic fallback, the form profile and
review-and-fill from [[Application-Assist|Application Assist]], and CV
surfacing. A long free-text field shows a **Draft** button that is **disabled**,
with the reason given plainly: drafting unlocks when the validator is wired and
its open defects are fixed. That is an honest empty state and a commitment
device.

### Phase three: generated answers behind the gate

§6, plus two prompt changes from the fabrication analysis that are cheaper than
the gate and reduce what it has to catch: drain the concrete degree and
institution values out of the CV format example, and label the two prose bodies
in the prompt so the posting reads as a target and the profile as the only
source of facts about the candidate.

## 8. Considered and rejected, and where the effort actually belongs

**Do not build:**

- **Auto-submit, in any form.** Not behind a confirm, not behind a setting, not
  for "simple" forms. The human click is the last gate and the audit trail.
- **A second ATS detector in Quiver.** §4. The fix for a failing adapter is
  upstream.
- **The drag-and-drop file experiment.** With a human-pick default it is dead
  weight, and [[Application-Assist|Application Assist]] already records it as
  unverified and secondary.
- **`chrome.debugger` plus `Page.printToPDF` for automatic CV saving.** Already
  dropped once, on 2026-10-08, after `debugger` turned out not to work as an
  optional permission. Manual save works today at no code cost. This is the
  clearest case in the design of effort that buys a keystroke.
- **An LLM-based claim verifier, or an LLM anywhere in the gates.**
- **A generated-answer cache keyed only on the question.** Key it on question,
  company and register version, or not at all. An answer that was clean under an
  older register is an unvalidated answer wearing a green tick.
- **Any copy, in this repository, of the claims register, the gate dictionary or
  the personal quota rules.** This repository is public. This is the single
  highest-consequence mistake available in this build, and it would look like a
  refactor.

**Where the effort is better spent, and the ordering is not the intuitive one.**
The generation path is worth more than any feature in phases two and three, and
it is cheaper. The validator's own open defects bound phase three's value from
above, and the two prompt edits in §7 are a handful of lines against what the
fabrication analysis calls the direct template for the observed failure. On a
small model, a concrete nearby example beats an abstract instruction nineteen
lines below it, so prompt hygiene matters more here, not less. Phase one is
independent of all of that and does not have to wait for it.

## 9. What is decided, what is open, what depends on work elsewhere

**Decided (design questions settled, nothing scheduled):** the shared-origin
Dexie handoff (§3); passing the ATS identity in rather than detecting it (§4);
the human picking the file, with `attachFileToInput` kept as an off-by-default
experiment (§5); generate-validate-show with no override (§6); the phase
boundaries, including form reading in phase one (§7).

**Open:**

- The consensus-spread threshold that triggers the disagreement warning is a
  **starting value, not a measured one.** Flow's database was not queried and
  the real distribution is unknown.
- Whether an MV3 extension page keeps the host-permission CORS exemption. Needs
  a spike. Until then, outbound HTTP goes through the service worker.
- Whether `attachFileToInput` survives each ATS's uploader. Never tested against
  a live form, which is a further reason not to depend on it.
- Scheduling. This is a proposal; none of it is on the roadmap in
  [[Plan|Development Plan & Backlog]] yet.

**Depends on work outside this repository:**

- Flow exposing `ats_identity` and its derived fields in both job responses,
  and the new apply-queue, outcome, CV-path and validation endpoints. Without
  the first of those, §4 cannot be built at all.
- Flow's apply-time gate module, which reads the same detectors Flow's ranking
  uses but applies blocking thresholds to them. Flow's ranking behaviour does
  not change.
- The validator's open defects, which are tracked outside this repository and
  which gate phase three (§6).
- Personal records parsing and write-back, which happens entirely on Flow's
  side. **Quiver never touches those files**, has no filesystem path to them,
  and should not acquire one.
