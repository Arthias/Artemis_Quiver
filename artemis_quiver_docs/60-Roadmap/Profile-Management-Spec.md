# Profile management: master, preferences, fingerprint

> [!NOTE] Status (2026-10-26): spec, nothing built
> Written against Quiver `feat/assisted-apply` @ `0be5870` and Flow `feat/assisted-apply` @ `079e059`.
> Open decisions are marked **(open)** with the default this spec assumes.

## 1. Goal

One profile per workspace profile, managed in one place (the Profile page), with two
derivatives generated from it and pushed to Flow automatically.

| Layer | What it is | Built from | Editable | Read by |
|---|---|---|---|---|
| **Master profile** | the user's markdown, as today | the user | yes | job analysis, CV/CL builders, Flow scoring and strategy |
| **Preferences** | a structured card: hard limits plus what the user wants | the master profile, by one LLM call | yes | Flow eligibility gates (today), Flow pre-score (later), the fingerprint |
| **Fingerprint** | a short single-line text | the preferences, by a template | yes | the overlay quick score (Gemini Nano or fallback) |

The product stays general-purpose: nothing about any particular user is hardcoded, and every
preference field is unset by default (unset = no filtering).

## 2. What it replaces

| Today | After |
|---|---|
| `profileMarkdown` on the profile record | unchanged |
| Flow preferences, edited in Settings → Flow, stored only in Flow (`backlog_config.preferences`) | **Preferences**, stored in Quiver and pushed to Flow |
| Candidate card in Flow's job-card experiment (`scripts/align_experiment.py`) | merged into **Preferences** |
| Fingerprint, generated by an LLM from the first 4,000 chars of the profile, in two places (`Config.tsx` `generateFingerprint`, `background.ts` `generateFingerprintFromProfile`), stored in `chrome.storage` | **Fingerprint**, rendered from Preferences, stored on the profile record |
| "Send Profile to Flow" button | automatic sync (§6) |
| Profile page "AI assistant" tab | removed for now (§4) |

The form profile (Settings → Apply, `formProfile:<id>`) is applicant form data, not a profile
derivative, and stays where it is **(open: move it to the Profile page as well?)**.

## 3. Data model (Quiver)

New optional fields on `ProfileRecord` (`db/schema.ts`) and `ProfileWorkspaceData`. They are not
indexed, so **no Dexie version bump**. Deleting a profile removes them with the record.

```ts
interface Derived<T> {
  value: T;
  /** SHA-256 of what it was built from: the master markdown for preferences, the preferences JSON for the fingerprint. */
  sourceHash: string;
  generatedAt: string;
  /** True once the user has edited it by hand since it was generated. */
  edited: boolean;
}

preferences?: Derived<ProfilePreferences>;
fingerprint?: Derived<string>;
```

`ProfilePreferences` is Flow's current `Preferences` model, minus its two operational fields,
plus the candidate-card fields:

| Field | Type | Gate / weigh | Source |
|---|---|---|---|
| `home_country` | ISO code \| null | gate | Flow today |
| `work_authorisation`, `remote_from`, `relocation_countries` | place codes | gate | Flow today |
| `work_modes.{remote,hybrid,onsite}` | null \| bool \| place list | gate | Flow today |
| `languages` | `{name, level?}[]` (CEFR or free text) | gate | Flow today (names only), level from the card |
| `has_degree` | bool \| null | gate | Flow today |
| `fields` | string[], plain-language work fields | weigh | card |
| `levels` | subset of entry / mid / senior / staff_principal / manager / director | weigh | card |
| `skills` | string[] | weigh | card |
| `years` | number \| null | weigh | new |
| `domains` | string[], industries | weigh | new |
| `schema_version` | 1 | — | new |

Zod schema in `types/preferences.ts`, shared by the editor, the generator and the sync.

`daily_cap` and `review_by` are Flow operating settings, not profile facts; they stay in Flow (§7).

## 4. Profile page

- **Tabs:** *Master profile*, *Preferences*, *Fingerprint*.
- **Remove the AI assistant tab** (chat UI and handlers in `pages/Profile.tsx`). Keep the stored
  `profileChat` data and `profileChatService.ts`, so the assistant can come back without a migration.
- **Header buttons:** Import, Export, Save as today, plus **Regenerate preferences and fingerprint**
  under Import/Export.
- **Preferences tab:** the editor moved from `components/flow/PreferencesSection.tsx`, extended with
  the card fields (list inputs for fields, skills, domains; checkboxes for levels; number for years;
  name + level rows for languages). It works without Flow connected (§5).
- **Fingerprint tab:** one textarea with a character count, plus a read-only line saying what it was
  rendered from.
- **Stale badge** on a tab when its `sourceHash` no longer matches its source: "Built from an older
  master profile — regenerate?". Nothing regenerates without the user pressing the button.

### Regenerate

1. Preferences: one LLM call over the **whole** master profile (no truncation), structured JSON,
   validated with the zod schema. The prompt uses `<placeholders>` only, never realistic example
   values (the 2026-10-22 experiment showed the model copies example values into the output).
   Anything the profile does not state is left unset, never guessed.
2. Fingerprint: rendered from the new preferences (below).
3. If either one has `edited: true`, confirm first, naming which one will be overwritten.
4. The result is shown in its tab for review before saving; generation never saves silently.

### Fingerprint render

Deterministic template, no LLM call:

```
<fields, top 2> | <skills, top 5> | <years>y | <domains, top 3> | <levels>
```

Unset parts are dropped; capped at 300 chars like today. **(open: template vs. an LLM summary of the
preferences.)** Default is the template, because it is instant, always current and has nothing to
go stale. Check it against the overlay before removing the old path: score a handful of labelled
postings with both and compare.

### Import / export

- Importing a master profile marks preferences and fingerprint stale; it does not regenerate them.
- Export stays master-only **(open: also export preferences + fingerprint as JSON?)**.

## 5. Preferences without Flow

Today's editor needs Flow for place codes (`GET /api/geo`) and validation (Flow's `Preferences`
validators). On the Profile page it must work with Flow absent:

- Country names and codes from `Intl.DisplayNames(["en"], { type: "region" })` (built into the browser).
- Region codes (`EUROPE`, `EU`, `EEA`, …) as a small constant copied from Flow's `eligibility.py`.
- Flow still validates on push; a rejected value is shown as a sync error, naming the field.

## 6. Sync to Flow

**Rule:** before Quiver controls Flow, Flow holds the current three layers.

- `profileHash` = SHA-256 of `master + preferences JSON + fingerprint`.
- New `ensureFlowSynced(baseUrl)` in `services/flowBridge.ts`:
  1. Reads the active profile record from Dexie.
  2. `GET /api/profile` → Flow's stored `hash`. If equal, done.
  3. Otherwise `PUT /api/settings/preferences` (preferences), then `PUT /api/profile`
     (`{content, path, hash, fingerprint, profile_name}`). The hash is written last, so a failed
     preferences push leaves Flow's hash stale and the next call retries.
  4. Caches the synced hash in memory, so repeated calls cost nothing until the profile changes.
- Called from:
  - **Connect** (Settings → Flow) and opening the `/flow` page;
  - **`flowPost` / `flowPut`**, the shared helpers every control call already goes through (search,
    rank, autopilot, strategy, job status, apply queue), skipped for the sync calls themselves;
  - **Profile save** while Flow is connected (debounced like autosave).
- A sync failure blocks the control call and shows the error; Flow is never driven against a profile
  Quiver knows is out of date.
- Settings → Flow shows "Flow has: <profile name>, synced <time>" instead of the Send button.
  `flowConfiguredAt` is set on the first successful sync plus an LLM config push.
- **Multiple workspace profiles:** Flow holds one profile. Controlling Flow from a different workspace
  profile replaces Flow's profile with that one. The Flow tab says which profile Flow has, so this is
  visible. **(open: warn before replacing?)**
- Not covered: the extension's background worker (capture, outbox). It does not change which profile
  Flow scores against.

## 7. Flow changes

| Change | Where |
|---|---|
| `Preferences` gains `fields`, `levels`, `skills`, `years`, `domains`, `schema_version`, and language levels. Gates ignore the new fields. Accept `languages` as plain strings too, for old clients. | `app/api/routes.py`, `app/pipeline/candidate.py` |
| `daily_cap` and `review_by` move out of the preferences JSON to their own settings (e.g. `GET/PUT /api/settings/apply`), so a preferences push from Quiver cannot reset them. One reader today: `apply_routes.py:35`. The daily-cap editor stays in Settings → Flow / Apply tab. | `app/api/routes.py`, `app/api/apply_routes.py`, migration in `app/db/connection.py` |
| `PUT /api/profile` accepts optional `hash`, `fingerprint`, `profile_name`; `GET /api/profile` returns them. Stored next to `profile.md`. | `app/api/routes.py`, `app/llm/profile.py` |
| Nothing reads the fingerprint in Flow yet; it is stored for a later quick pre-score. | — |

Not in scope: re-scoring jobs after the profile changes. Flow still never re-scores
(Flow `README.md`); jobs scored against an older profile keep their scores.

## 8. Removals in Quiver

- Settings → Extension: fingerprint section and `generateFingerprint` (`pages/Config.tsx`).
- Extension popup: the generate-fingerprint button becomes a link to the Profile page; the popup
  still shows whether a fingerprint exists and its date.
- `background.ts`: `generate_fingerprint` handler and `generateFingerprintFromProfile`. The overlay
  reads the fingerprint from the profile record via `extension/idbProfile.ts` (which already reads
  the active record), not from `chrome.storage`. The overlay's score cache stays keyed by fingerprint
  text, so a new fingerprint invalidates old quick scores as today.
- Settings → Flow: *Send Profile to Flow* button and `PreferencesSection` (moved to the Profile page).

## 9. Checks

One small test file each, no new framework:
- preferences zod schema accepts Flow's current shape and rejects bad place codes;
- the fingerprint render drops unset parts and caps at 300 chars;
- `ensureFlowSynced` makes no PUT when Flow's hash matches, and writes preferences before the profile;
- Flow: `PUT /api/settings/preferences` leaves `daily_cap` untouched; old `languages: string[]` still parses.

## 10. Order of work

1. Flow: `Preferences` fields, split `daily_cap`/`review_by`, hash on `/api/profile`.
2. Quiver: data model, Profile page tabs (assistant removed), preferences editor moved and working
   without Flow.
3. Quiver: regenerate (LLM preferences + template fingerprint), stale badges.
4. Quiver: `ensureFlowSynced` and the Settings → Flow status line; remove the Send button.
5. Quiver: extension reads the fingerprint from the record; remove the old generators.

Each step ships on its own; after step 2 the old fingerprint path still works until step 5.
